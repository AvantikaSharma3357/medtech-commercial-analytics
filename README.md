# Medtech Commercial Analytics

A small, tested analytics application for the commercial team of a fictional medical imaging company. It turns Salesforce-style CRM data into governed KPIs for sales leadership, pipeline management, and customer usage, with row-level security and automated data quality checks.

> All data in this repo is **synthetic**, generated by `data/generate_data.py`. No real customers, people, or company data are used.

## What it does

| Tab | Questions it answers |
|---|---|
| Commercial performance | Bookings, deals won, win rate, and average deal size by year, month, region, and product |
| Pipeline | Open pipeline by stage and the top accounts by open pipeline |
| Customer usage | Monthly analyses ordered, active accounts, and analyses per account by product |
| Data quality | Results of every CRM data quality check, with severity |
| Metric definitions | The metric catalog, read directly from the semantic model |

The sidebar has a **View as** selector. Switching from the admin to a regional manager or a sales rep changes every number on the page, because access rules are enforced inside the query layer rather than in the UI.

## How it's built

```
data/generate_data.py   Synthetic Salesforce-style extracts (User, Account, Opportunity, monthly orders)
data/raw/*.csv          Committed extracts; CI regenerates them and fails if they drift
semantic/metrics.yml    Semantic model: cubes, measures, and dimensions defined once as code
semantic/access.yml     Role-based access control and row-level security rules
src/mca/warehouse.py    Loads extracts into an in-memory DuckDB warehouse
src/mca/semantic.py     Compiles metric requests into parameterized SQL and applies RLS
src/mca/access.py       Resolves each user's role into a row filter
src/mca/quality.py      SQL data quality checks (errors fail CI, warnings are reported)
app.py                  Streamlit dashboard; every number comes from the semantic layer
tests/                  pytest suite: metrics, access control, data quality, data generation
.github/workflows/ci.yml  Lint, data drift check, quality checks, tests, and app smoke test
```

### Semantic layer

Business metrics are defined once in `semantic/metrics.yml`, following the same ideas as semantic layers like Cube: each cube has a base table, joins, **measures**, and **dimensions**. Ratio metrics such as `win_rate` and `avg_deal_size` are composed from base measures, so they can't drift from the numbers they're built on.

```yaml
win_rate:
  type: ratio
  numerator: closed_won_count
  denominator: closed_count
  format: percent
```

The app asks for metrics by name:

```python
model.query("opportunities", ["closed_won_amount", "win_rate"], user,
            dimensions=["region"], filters={"product": ["Stenosis Mapping"]})
```

Only measures and dimensions defined in the model are accepted, and filter values are always passed as bound parameters, never pasted into SQL.

### Access control and row-level security

`semantic/access.yml` maps roles to row filters:

| Role | Sees |
|---|---|
| `admin` | All rows |
| `regional_manager` | Accounts in their region |
| `rep` | Only accounts they own |

The filter is added to every compiled query after user-supplied filters, so a caller can't widen access by filtering on another region. The model also refuses to load if any cube is missing a dimension that the access rules depend on.

### Data quality

`src/mca/quality.py` runs SQL checks against the CRM extracts, including unique IDs, orphaned opportunities, invalid account owners, Closed Won deals without an amount, close dates before create dates, stage names that disagree with the IsClosed / IsWon flags, and missing billing states. Errors fail CI. Warnings are shown in the dashboard.

## Engineering workflow

- Changes go through **pull requests** on feature branches.
- **GitHub Actions** runs on every pull request: `ruff` lint, a check that the committed data matches the generator, the data quality suite, the pytest suite, and a headless smoke test that renders the Streamlit app.
- `main` is intended to be protected so CI must pass before merging.

## Run it locally

```bash
pip install -r requirements-dev.txt
streamlit run app.py            # dashboard
pytest                          # tests
PYTHONPATH=src python -m mca.quality   # data quality report
python data/generate_data.py    # regenerate synthetic data
```

## Notes

- Product names, accounts, and users are invented. Field names mirror common Salesforce objects so the logic carries over to a real CRM extract.
- DuckDB stands in for a cloud warehouse such as Redshift; the semantic layer emits standard SQL.
- Built with AI-assisted development (Claude Code).
